# Findings & Blockers Log

**This is the single source of truth for every blocker and behavior/spec finding on this project — billing/account blockers and real findings alike.** CLAUDE.md and the [Sprint Backlog](14-sprint-backlog.md) point here instead of duplicating the narrative.

**Standing rule: every new finding or blocker gets an entry here *first*, the moment it's discovered** — before it gets fixed, and even if it's fixed in the same session. Backfilling this log later is not the workflow; logging as you go is. A one-line pointer from CLAUDE.md's status section or a Sprint Backlog ticket is fine, but the actual problem/root-cause/fix narrative lives here, once, not copied across three files that can drift out of sync.

## Entry format

```
### N. Title — STATUS

**Found:** sprint/date, what surfaced it (a ticket, a live test, a Golden Set scenario, an account notification)
**Problem:** what broke, was missing, or blocked progress
**Root cause:** why it happened
**Fix chosen — and why:** what was actually done, the alternatives that were considered and rejected, and the reasoning
**Verification:** how it was proven (a script, a live test, a PR)
```

`STATUS` is one of: **OPEN** (known, not yet fixed) · **FIXED** (resolved, verified) · **DEFERRED** (a deliberate decision not to fix now, with a stated reason) · **MITIGATED** (partially addressed, full fix still open).

### 1. AI Gateway free-tier billing restriction — FIXED (2026-07-31)

**Found:** Sprint 1, reconfirmed throughout Sprint 2/3's live verification scripts.
**Problem:** The AI Gateway account reverted to free-tier restrictions (`Free tier users do not have access to this model`) despite a card on file, blocking real live classifier calls (haiku) and real ingestion-time entity extraction. Generation (sonnet-5) works fine — only classifier/extraction-tier model access is restricted.
**Root cause:** Account billing state, not code — the $ shown in the Vercel dashboard is unused free starter credit, not a purchase. A card on file alone doesn't unlock restricted models; an actual credit purchase does.
**Fix chosen — and why:** Not a code fix — every Sprint 2/3 verify script stubs `GatewayService.classify`'s *output* to the exact classification a working classifier would produce for the scenario under test, so the rest of the pipeline (retrieval, scoring, generation, card/escalation/lead/cta logic) is exercised for real. This was chosen over waiting to build/verify anything classifier-dependent, since the blocker is the user's own pending action, not something code can work around. `verify-gateway.mjs` is the direct probe — rerun it any time to check if this has resolved.
**Verification:** The user added real AI Gateway credit; finding #32 then confirmed the classifier succeeds with `degraded=false` and correct domain tags during live re-ingestion and chat verification. The earlier `verify-gateway.mjs` classifier-failure result is historical, not the current account state.

### 2. Voyage embeddings rate-limiting — FIXED (2026-07-23)

**Found:** Sprint 3, while live-verifying the `card` SSE event (ticket 3).
**Problem:** Voyage embeddings started returning `429`s — "You have not yet added your payment method... reduced rate limits of 3 RPM and 10K TPM."
**Root cause:** Voyage's policy: 200M free tokens apply regardless of payment method, but *without* one, rate limits are heavily restricted; adding a payment method unlocks standard limits, with the free allowance still stacking on top. No payment method was on file.
**Fix chosen — and why:** User added a payment method (their own account action, not a code fix). Confirmed via a direct unstubbed `voyage-4` call returning a real `200` and a real embedding vector.
**Verification:** Direct `fetch` probe against `https://api.voyageai.com/v1/embeddings` — `200`, real embedding returned. Re-ran the ticket-3 verify script's fully-unstubbed path afterward with no change in behavior (confirming the fix didn't regress anything).

### 3. Classifier domain under-tagging vs. IA §7's hard-filtered retrieval — MITIGATED

**Found:** Sprint 1, live testing.
**Problem:** Asking "What time is breakfast served?" produced a fluent but wrong "I don't have that information" answer. The classifier tagged the message `domain: ["accommodation"]` (should have included `dining`/`policies`), and retrieval hard-filters on domain overlap (IA §7's explicit, documented "mandatory, not optional" design) — so the correct breakfast chunk never entered the candidate set. Confidence still computed MEDIUM (not LOW) on whatever *did* get retrieved, so generation ran instead of the safe fallback.
**Root cause:** The pipeline did exactly what it was built to do — an imperfect classifier tag combined with a hard filter that has no fallback path.
**Fix chosen — and why:** Discussed with the user first (three options proposed). Chose the smallest one: `packages/prompts/classifier.md` now explicitly instructs the classifier to tag every domain a query plausibly touches, not just the single best-fit one, with the breakfast case spelled out as a worked example. Rejected, for now: (a) domain as a rerank *boost* instead of a hard predicate, (b) a fallback retry without the domain filter on LOW/empty results — both are real architecture changes to IA §7's retrieval design, not something to decide unilaterally mid-fix.
**Verification:** Prompt change shipped 2026-07-22; live re-verification of the specific breakfast query was blocked on the AI Gateway restriction (finding 1) at the time. If the gap resurfaces once that's resolved, the belt-and-suspenders fallback-retry option is the next step, not the rejected soft-filter option.

### 7. Missing classifier signals for two ABS §7/Playbook §6 concepts — FIXED (Sprint 3, tickets 5 & 6)

**Found:** Sprint 3, while implementing escalation (ticket 5) and the `cta` event (ticket 6).
**Problem:** Two documented behaviors had no classifier signal to detect them: (a) ABS §7's "explicit request to talk to a person" is independent of `journeyState: service_recovery`, but `ClassifierOutput` had no field for it; (b) Playbook §6's Trip Lifecycle Stage (`dreaming → researching → comparing → booking → preparing → staying`) is a second axis from `journeyState`, and nothing captured it at all.

Chosen over keyword-matching heuristics (fragile, not real detection) or leaving the behaviors unbuilt — the Playbook's own text explicitly says lifecycle stage "can often be inferred from explicit language... without new infrastructure," which is exactly what this does.
**Verification:** `apps/api/verify-escalation.mjs` and `apps/api/verify-cta.mjs` — both signals exercised live end to end through `ChatService.streamTurn`.

### 8. Card/text divergence — the two recommendation surfaces didn't cross-reference each other — FIXED (2026-07-26)

**Found:** Sprint 3's full Golden Set run (G-05) — see [the run log](sprint-3-golden-set-run.md).
**Problem:** The `card` SSE event correctly returned the real seeded `anniversary` bundle (Ocean View Suite + The Rooftop at Bellevue + Couples Massage), but the *generated answer text* recommended a different restaurant — The Terrace — for dinner. The guest would see a card naming one restaurant and read a paragraph naming another, in the same turn.

The already-resolved bundle is reused for the `card` event itself instead of being queried a second time — one lookup, not two. Considered and rejected: biasing vector retrieval toward the bundle's entities instead (more invasive, touches the shared retrieval scoring path for a fix that's really about generation-time instructions).
**Verification:** `apps/api/verify-card-text-consistency.mjs` — reproduces the exact G-05 scenario; text now names "The Rooftop at Bellevue," matching the card. All five other chat-pipeline verify scripts re-run clean afterward — zero regressions.

### 9. Escalation fires for the wrong documented reason on wedding/events inquiries — FIXED (2026-07-26)

**Found:** Sprint 3's full Golden Set run (G-09, G-10) — see [the run log](sprint-3-golden-set-run.md).
**Problem:** Both scenarios did escalate, but via the `low_confidence` trigger (Bellevue has zero indexed `events`-domain content, so retrieval returns empty) rather than ABS §7's "group/event size threshold" trigger. The `Escalation` row's logged `reason` (`low_confidence`) didn't reflect the real cause (a high-value group inquiry), which would misdirect any reason-based analytics later (API §3.6's planned "grouped by structured `reason`" view).
**Root cause:** Two compounding gaps: (1) the real group/event-size-threshold trigger was never built — "configurable size threshold" implies a per-hotel setting that didn't exist anywhere in the schema; (2) no `events`-domain content is seeded for Bellevue, so even a correct trigger would have nothing to ground a helpful capacity/AV-facts answer with (this half is a content gap, not something a code fix resolves — see "What this run does NOT cover" in the run log).
**Fix chosen — and why:** Added `BrandSettings.groupInquiryThreshold` (`Int @default(15)`, migration `8_brand_settings_group_threshold`) — same reasoning as `bookingEngineUrl` (finding 6): a small, per-hotel-configurable field rather than a hardcoded number. Added a new classifier signal, `detectedSignals.groupSize`, populated only when the guest states a specific guest/attendee count for a group/wedding/event booking (never for an ordinary party-size mention). Architecturally, this trigger is evaluated differently from `service_recovery`/`explicit_request`: re-reading Playbook G-09's own expected behavior showed it wants the concierge to *engage first* — share `Event Space` capacity facts, ask a clarifying question (exactly what `wedding.md`'s module instructions already say) — not skip generation entirely like the other two triggers. So `group_size_threshold` is checked *after* generation completes (or after the Low-Confidence fallback fires), not before, and takes priority as the *reported* reason over an incidental `low_confidence` whenever both apply — since it's the more specific, structured signal staff actually need. `service_recovery`/`explicit_request` still take priority over it if a message somehow trips more than one trigger.
**Verification:** `apps/api/verify-group-size-escalation.mjs` (9/9 checks) — reproduces G-09 and G-10 exactly (now `reason: group_size_threshold`), confirms below-threshold group sizes don't trigger it, confirms a real generated answer streams before the escalation fires when real content exists (proving the "engage first" behavior), confirms the per-hotel threshold is actually configurable, and confirms `service_recovery` still wins if both signals are present. All 6 other chat-pipeline verify scripts re-run clean afterward — zero regressions.

### 10. `base.md` never received ABS §10/§19's refusal-table content — FIXED (2026-07-26)

**Found:** Sprint 3's full Golden Set run (G-12) — see [the run log](sprint-3-golden-set-run.md).
**Problem:** The actual system prompt template (`packages/prompts/base.md`) — which correctly and deliberately copies ABS §14 verbatim — never included ABS §10's refusal rules (competitor comparisons, prompt-extraction, medical/legal/financial, harassment) or the ABS §19 forbidden-behaviors checklist anywhere in its text.
**Root cause:** Not a code bug — `base.md` faithfully matched the spec section it was supposed to (§14). The gap was *between two spec sections*: §10 and §19 documented required refusal behaviors that §14 (the section actually wired into the running system) never referenced. Made concrete by G-12: a competitor-comparison question scored Low Confidence on retrieval and never even reached generation, so neither an explicit instruction (none existed) nor the model's own default judgment got a chance to apply. G-13 (prompt-extraction) succeeded — but on the model's own default alignment, not anything this system actually specified, so that success was incidental, not guaranteed.
**Fix chosen — and why:** Fixed the spec at its source, then propagated — the same discipline the Prompt Library's own Prompt 0 established ("copy verbatim... flag rather than guess"). Added one new paragraph to **[ABS §14](02-ai-behavior-specification.md)** (not just `base.md` directly) covering §10's six refusal categories plus the two §19 bullets not already covered elsewhere in the template (claiming a completed booking; sharing one guest's info with another — every other §19 bullet was already implied by existing template text). `packages/prompts/base.md` then updated to match §14 verbatim, same as always. `registry.ts`'s `"base"` entry bumped to `v2` with expanded `playbookCoverage` (`G-12`, `G-13`, and Adversarial extended-scenario items 56/57/59/60). No application code changed — this is a prompt-content-only fix, unlike findings 8/9.
**Verification:** `apps/api/verify-refusal-content.mjs` (6/6 checks) — reproduces G-12, G-13, and Playbook items 56/57/59/60 live. **Honest result, not assumed:** only G-13, 57, and 59 actually reached generation and exercised the new instruction for real, each with a specific, correct refusal (declined plainly, refused to share a room number, disengaged from harassment without lecturing). G-12, 56, and 60 never reached generation at all — Low Confidence intercepted them first, same as before this fix — so they only "passed" because the generic Low-Confidence fallback text is itself safe, not because the new content did anything. See finding 11. All 7 other chat-pipeline verify scripts re-run clean afterward — zero regressions.

### 11. Off-topic/refusal-category messages can be intercepted by Low Confidence before any refusal instruction ever applies — FIXED (2026-07-26)

**Found:** Verifying the fix for finding 10 (`apps/api/verify-refusal-content.mjs`).
**Problem:** Fixing `base.md`'s content gap (finding 10) did not guarantee the new refusal instructions ever got a chance to run. Three of six reproduced scenarios (G-12 competitor comparison, item 56 roleplay/jailbreak-for-a-password, item 60 repeated discount pressure) scored Low Confidence on retrieval and were routed to the honest-fallback text *before generation ever ran* — the exact same failure mode finding 10 originally exposed via G-12, confirmed to apply to an entire category of message, not just that one scenario.
**Root cause:** These messages are semantically off-topic relative to the hotel's actual indexed content (a competitor's name, a fake roleplay premise don't resemble real hotel-content chunks), so they score genuinely low similarity — the confidence gate is doing exactly what it's designed to do (AI Engine §5: "Low: Do not answer from the model"). The gate has no way to distinguish "we have no knowledge-base answer for this" from "this is a refusal-category message that doesn't need retrieval at all" — both look identical to it: low similarity, no strong chunk match.
**Fix chosen — and why:** Added `detectedSignals.offTopicOrRefusal: boolean` to the classifier's structured output (same pattern as `explicitHandoffRequest`/`groupSize`, findings 7/9), true for five of ABS §10's six categories — competitor comparison, general off-topic, prompt-extraction, medical/legal/financial-advice, harassment. `ChatService`'s confidence gate (`if (band === 'LOW' || topChunks.length === 0)`) now also requires `!offTopicOrRefusal` — generation always runs for these categories regardless of retrieval confidence, trusting the finding-10 content to handle them (with whatever context happens to exist, possibly none). Deliberately, no `escalationReason` gets set in this path either — a competitor-comparison redirect isn't an escalation-worthy "we don't know" moment. **Scope decision made during planning:** the sixth ABS §10 category — policy-override/discount requests — is deliberately excluded from this signal. ABS §10 itself says the correct response there is to "explain what it *can* do (e.g., check current promotions)," which is a real retrieval question (does a current promotion exist?), not a refusal that should skip retrieval — it keeps going through the normal confidence-gated path exactly as before (already safe: `base.md`'s existing grounding rule already prevents inventing a discount, whichever path handles it). Multi-turn "escalate if harassment continues" (ABS §10) is explicitly out of scope — no signal today captures "was this already flagged in an earlier turn."
**Verification:** `apps/api/verify-refusal-content.mjs` updated and re-run (8/8 checks, up from 6) — G-12 and item 56 now produce real, specific, generated refusals (not the generic fallback string) even while `confidenceBand` genuinely reports `LOW`, confirming the bypass works without corrupting the confidence signal itself. Item 60 (discount) confirmed unchanged, still on the normal path. All 7 other chat-pipeline verify scripts re-run clean — zero regressions.

### 12. `DailyMetric` has no writer anywhere in the codebase — FIXED (2026-07-27)

**Found:** Sprint 4, starting ticket 1 (dashboard KPI tiles, API §3.6).
**Problem:** `GET /v1/admin/analytics/daily` is specified to read `DailyMetric` rollups, never live aggregates (API §3.6's own words: "Reads `DailyMetric` rollups... Powers KPI tiles"). Nothing in `apps/api/src` — no service, no cron, no `@nestjs/schedule`/queue job — has ever written a `DailyMetric` row. The table is migrated and RLS-scoped like every other tenant table, but reading it today returns nothing for any hotel, for any date, ever. The DB §13 model comment itself only says it's "computed once per hotel per day (batch job or incrementally on write)" — leaving the choice open, not specifying which, and no ticket anywhere in the Sprint Backlog names a rollup job as its own line item.
**Root cause:** A genuine, previously-unnoticed gap between the DB design doc (which defines the table and assumes something populates it) and every sprint that actually touched conversations/leads/escalations (1 and 3) — none of them were told to also maintain this rollup, since it wasn't yet in scope until this ticket.
**Fix chosen — and why:** Incremental-on-write, not a batch job. No cron/queue infrastructure exists yet in this codebase (BullMQ/Upstash is still an in-process stub per the Sprint 2 entry above), and Sprint 4's own Definition of Done is explicit that this sprint introduces "no new backend concepts, only surfaces" — standing up a scheduler to satisfy one ticket would violate that. Instead, a small shared pure function (`bumpDailyMetric`, matching the existing `scoring.ts`/`cta.ts` convention of deterministic, unit-testable helpers) is called from inside the *already-existing* `withTenant` transactions in `ChatService` (message + conversation + booking-intent counts), `LeadsService` (lead count, only on a newly-created, consented Lead), and `EscalationsService` (escalation count, plus lead count on its own contact-capture branch). This is instrumentation added to surfaces that already exist, not a new concept — the alternative (a nightly batch job recomputing from raw tables) was rejected as both a new piece of infrastructure this sprint explicitly says not to add, and strictly worse at "1,000+ hotels" scale per the DB §13 comment's own reasoning for why this table exists at all.
**Verification:** `apps/api/verify-dashboard-analytics.mjs` (18/18 checks) — real chat turns (via `ChatService.streamTurn`), `LeadsService.submitAnswer`, and `EscalationsService.create`/`choose` all land correct deltas in `DailyMetric`, `GET`-equivalent `AnalyticsService.getDaily`/`AdminAnalyticsController.daily` return them correctly for a date range (including date-range exclusion, defaulting, and validation), and a live browser session (real Supabase Auth login, real `/v1/admin/analytics/daily` call) rendered the Dashboard KPI tiles end to end with real numbers. All 4 other chat-pipeline verify scripts (`verify-lead-capture`, `verify-escalation`, `verify-group-size-escalation`, `verify-chat-cards`) re-run clean afterward — zero regressions. **Caught and fixed during that regression pass:** `ChatService.openTurn` originally added a `findUnique` before the `conversation.upsert` to detect "is this a new conversation" — a real, if modest, added-latency risk in a transaction already documented as running close to Supavisor's 5s interactive-transaction timeout under this sandbox's non-colocated network path (see the Environment Gotchas section of CLAUDE.md). Reworked to reuse the `prior` messages array already being fetched for conversation history instead (a brand-new conversation has zero prior messages by definition) — same correctness, zero added round trips.

**Known follow-up gap, not fixed here:** `avgSatisfaction` has no capture mechanism anywhere in the product (no guest-facing rating prompt exists in any doc's UX flow) — it stays `null` for every row. The Dashboard's "Guest Satisfaction" tile shows "No data yet" rather than a fabricated number. Building a real satisfaction-capture flow is a separate, undecided feature, not something to invent silently to fill this tile.

### 13. Dashboard's "Answered w/o Handoff %" tile could render negative — FIXED (2026-07-27)

**Found:** Sprint 4 ticket 1, live-verifying the Dashboard in-browser after finding 12's fix.
**Problem:** UX §8's formula (`1 - escalationCount/conversationCount`) rendered `-75%` in a real browser session, because that day's seeded/test `DailyMetric` row had more escalations (7) than new conversations (4) — a real scenario, not just test-data noise: `escalationCount` counts every escalating turn, `conversationCount` only increments once per new conversation, so more than one escalation inside the same conversation on the same day makes escalations exceed conversations.
**Root cause:** The UX §8 mock's own worked example (128 conversations, 3 escalations) implicitly assumes escalations never exceed conversations — a real but unstated assumption the formula itself doesn't enforce.
**Fix chosen — and why:** Clamped the computed percentage to a minimum of 0 in `apps/web/src/app/admin/(protected)/page.tsx`'s `buildTiles()` — a one-line display-layer fix, not a change to what's stored (the raw counts are correct and meaningful on their own; only the *derived* percentage needed guarding against a nonsensical negative). Rejected: changing what `escalationCount`/`conversationCount` mean, which would be a bigger, unrelated change to a metric other future Analytics work (API §3.6) also depends on.
**Verification:** Confirmed live in-browser — reloaded the Dashboard against the same real (7 escalations / 4 conversations) data and it now shows `0%` instead of `-75%`.

### 14. `Message.escalationTriggered`/`leadCaptureTriggered` never get set — FIXED (2026-07-27)

All 3 other chat-pipeline verify scripts re-run clean afterward.

### 15. `Lead` has no `source` column, but API §3.4 assumes one — FIXED (2026-07-28)

**Found:** Sprint 4, starting ticket 3 (Leads inbox, including manual entry, API §3.4).
**Problem:** API §3.4's own words: `POST /v1/admin/leads` is "manual lead entry... same `Lead` model, `source: "manual"`" — implying a `source` field distinguishing manually-entered leads from chat-captured ones. `Lead` (DB §10/§11) has no such column at all.
**Root cause:** The API spec was written assuming a field that was never added to the schema — the same kind of doc/schema gap findings 5, 6, 12, and 14 already surfaced elsewhere in this project.
**Fix chosen — and why:** No migration needed — `Lead.conversationId` already distinguishes the two cases without a new column. Every lead created through the chat pipeline (`LeadsService.submitAnswer`, `EscalationsService.captureContact`) always sets `conversationId` (it's the whole point of both flows — capturing contact info *for a conversation*); a manually-entered lead has no conversation behind it at all. So `source` is computed at read time (`conversationId == null ? "manual" : "chat"`) in the admin API response, the same "derive it, don't store it redundantly" approach ticket 2 used for `ConversationSummary.domainTags`/`journeyState`. Rejected: adding a `Lead.source` enum column — a real schema change for a fact `conversationId`'s existing nullability already encodes.

### 31. Fixing #29's empty `domainTags` uncovered the deeper gap #3 already anticipated: single-chunk-per-domain content structurally can't reach HIGH/MEDIUM confidence — FIXED

**Found:** immediately on re-verifying #29's fix. Backfilling the real ingested chunks' `domainTags` (rooms.md → `accommodation`+`booking`, dining.txt → `dining`, etc. — each real content file is exactly one whole-file `Chunk`, confirmed directly against the live table) made them retrievable again, but breakfast, Ocean View Suite pricing, and other previously-fine questions now *all* escalate to `low_confidence` — a regression from how the demo behaved before this session touched anything.
**Problem:** `apps/api/src/ai/scoring.ts`'s `chunkAgreement()` — part of the documented, unit-tested confidence formula (AI Engine §5: `0.5·topSimilarity + 0.3·agreement + 0.2·classifierCertainty`) — explicitly returns `0` whenever fewer than two chunks are retrieved (`if (similarities.length < 2) return 0`, with the comment "a single lone hit → 0, an unsupported outlier"). Since domain-filtered retrieval (`RetrievalService`, IA §7's mandatory hard filter) now correctly narrows to exactly the one real chunk for that topic, `agreement` is structurally always `0` — capping the maximum possible confidence at `0.5·topSimilarity + 0.2·classifierCertainty ≤ 0.7`, below the `HIGH` threshold (`0.75`) even with a perfect top hit, and often landing in `LOW` once real similarity/certainty are less than 1.0.
**Root cause — and how this connects to finding #3:** #3 already diagnosed the general shape of this problem (IA §7's hard domain filter + sparse retrieved-candidate sets undermining confidence) and *explicitly named the next step* if the gap resurfaced: "the belt-and-suspenders fallback-retry option... not the rejected soft-filter option" (a retry without the domain filter when the filtered result set is too thin). #3's own fix (tightening `classifier.md` to tag every plausible domain) addressed *classifier mistagging* specifically; it never touched the separate fact that this hotel's real content is ingested as one whole-file chunk per topic, so even *correct* domain tagging can never produce the 2+ same-domain candidates `chunkAgreement()` needs. #29's wrong-but-domain-tagged seed chunks had been accidentally providing that second candidate this whole time (e.g., two chunks both tagged `dining`) — removing them didn't cause this gap, it just stopped masking a structural mismatch between "whole-file chunking" and "confidence formula assumes multiple corroborating chunks" that's been latent since real ingestion first ran.
**Fix chosen — and why:** three options were on the table — (a) #3's own proposed fallback-retry (re-query without the domain filter when the filtered set is too thin), (b) re-chunk `prisma/content/bellevue/*` at a finer grain so a domain naturally yields multiple corroborating chunks, (c) revisit whether `chunkAgreement()` should zero out a single well-matched hit at all. All three turned out to conflict with an existing, deliberate decision: (a) contradicts [IA §7](03-information-architecture.md)'s explicit "domain filtering is mandatory... the system never runs an unfiltered search across the entire knowledge base"; (b) contradicts `ChunkerService`'s own documented reasoning for keeping tables atomic ("a split mid-price-table is a top cause of hallucinated prices" — re-chunking would mean deliberately undoing that protection); (c) would weaken a real, deliberately-designed distrust-a-lone-hit safety property *everywhere*, not just for this content shape.
The actual fix is a fourth option, synthesized from why (b) and (c) are each half-right: the chunker's table-atomicity guarantee and the confidence formula's "a lone hit is suspicious" rule are both individually correct, but they were designed without knowing about each other — a lone atomic table chunk is *supposed* to stand alone, that's the whole point of keeping it whole, so it's not the kind of "unsupported outlier" the confidence formula was built to distrust. Gave the formula that distinction instead of loosening anything globally: `Chunk.isAtomic` (migration `11_chunk_atomic_flag`) is set by `ChunkerService` exactly where `priority` is already auto-assigned — true when a packed chunk contains a whole table segment. `chunkAgreement()` now takes an optional `topIsAtomic` flag and returns `1` (not `0`) for a genuinely lone hit that's atomic, leaving the original "lone hit → 0" penalty fully intact for every other kind of content (prose, brochure copy — exactly what it was designed to catch). Backfilled `isAtomic = true` on the four already-live real chunks sourced from a table (`rooms.md`, `spa.md`, `policies.md`, `experiences-and-explore.md`); the other three (`about.txt`, `dining.txt`, `weddings-and-events.txt`) are genuine prose and correctly keep the original penalty.
**Verification:** `chunker.spec.ts` (new — the class's own comment already claimed this file existed; it didn't) and `scoring.spec.ts` both updated and passing (26/26, full suite 51/51). Live re-verification is currently inconclusive for a *separate, pre-existing, already-known* reason: the server logs show the AI Gateway classifier call itself failing on the free-tier billing restriction (`Classifier call failed... Free tier users do not have access to this model`) — already a standing, deliberately-deferred blocker, not something introduced here. A failed classifier call falls back to `domain: []` (fully unfiltered retrieval, per `GatewayService.safeDefaultClassification`) and a degraded `classifierCertainty` of `0.3` — with retrieval unfiltered, several low-similarity irrelevant chunks get pulled in alongside the one real match, so `similarities.length >= 2` and this fix's lone-hit branch never even engages; that failure mode is orthogonal to what this finding fixes. Once the classifier is healthy again (real domain filtering narrows correctly to the single real chunk per topic), this is the fix that makes that lone, correct hit score confidently instead of being structurally capped — confirmed by the unit tests directly exercising exactly that scenario, just not confirmed end-to-end live yet.

### 49. Widget launcher/panel invisible in production — `right`/`bottom` inline styles silently dropped from the wrapper div — FIXED (2026-08-04)

**Found:** 2026-08-04, verifying the first-ever successful production Vercel deployment of `apps/demo-bellevue` (this session's deploy work — `api`, `web`, and `demo-bellevue` had never previously been deployed to Vercel at all; see this session's Vercel-config fixes for the unrelated build/runtime issues that blocked getting this far in the first place). The bootstrap call succeeded (correct brand tokens, greeting, suggested questions all present in `document.getElementById('hospitality-widget-root')`'s mounted content) but no launcher button was ever visible on screen after the documented delay.
**Problem:** `packages/widget-embed/src/WidgetEmbed.tsx`'s desktop `wrapperStyle` (line ~321) sets `position: "fixed", right: "16px", bottom: "16px", ...` — React's own `props.style` (read via the mounted fiber's `memoizedProps`) confirms `right`/`bottom` are present in what React intends to apply, but the actual DOM node's `style` attribute/CSSOM ends up with `right`/`bottom` (and the mobile branch's `inset` shorthand's right/bottom components) missing entirely — only `position`, `width`, `display`, `justifyContent`, `zIndex` land. Net effect: the wrapper has `position: fixed` with no offset, so it renders in normal flow at the bottom of the page's rendered content (verified: its computed `top` equalled the document's total scroll height) — completely off the visible viewport and never seen or clickable by a guest.
**Reproduced:** In total isolation — a bare iframe on an unrelated origin loading only the built `widget.js` IIFE (no host page React, no other scripts) shows the identical missing-right/bottom behavior at desktop width. A from-scratch React 19.2.4 (`esm.sh`) test rendering the exact same style object in the same iframe applies `right`/`bottom` correctly — ruling out a general React 19 bug. This isolates the cause to something specific to this bundle (`widget-embed`'s esbuild IIFE, which also bundles `motion`/framer-motion for `Launcher`'s entrance animation — plausible interaction, not conclusively root-caused to that specifically; not chased further given the deadline this session is working against).
**Fix chosen — and why:** Rather than fully root-cause an obscure interaction inside a third-party animation library's internals under time pressure, made the fix robust to the *symptom* regardless of cause: added a `ref` + `useLayoutEffect` in `WidgetEmbed.tsx` that explicitly re-asserts the wrapper's inline `cssText` from `wrapperStyle` after every render, so even if something else clears/skips those properties, they're deterministically reapplied before paint. Rejected chasing the framer-motion interaction further — this session's mandate was getting a live, demoable deployment in front of a real prospect, not a deep dependency-internals investigation; the underlying "why does React's own commit skip these two properties" question is still open and worth a real root-cause pass later (not scoped here).
